# FHEC V2 CoFHE — Phase 10 and Phase 11 architecture

## A. Outcome and scope

Phase 10 provides independently implemented, reproducible mock differential verification over every CoFHE unsigned-width family currently supported by the FHEC V2 backend. Phase 11 packages all relevant exact-byte inputs and local outputs into an offline, self-contained, independently replayable dossier. The objective is stronger correctness evidence and grant-review reproducibility without adding dependency drift, writing to existing code, or silently moving into expensive live network operations.

The patch follows the proven Phase 8/9 source-generation path. It consumes an exact `prepared-phase89.json` record generated by a successful Phase 8/9 local preflight, not an untrusted shell string with an arbitrary Solidity directory. It checks the prepared record's project identity, known Arbitrum Sepolia chain ID used for the predecessor plan, code generation and mock-preflight flags, source/plan hashes, source directory boundary and fresh source seal. This is a provenance check; it does not imply the new phase itself sends any network requests.

The immutable predecessor assumption is crucial because a compiler-fuzzing suite that silently tests a different Solidity revision would be nearly useless. The compiled libraries, wrappers and reference implementations must be exactly those preflighted in the earlier source directory. A source-seal mismatch prevents the new suite from running.

## B. Why an independent oracle matters

The earlier Phase 6 oracle generated a boundary corpus and the Phase 7/8/9 test harnesses performed differential comparisons against reference Solidity implementations. This is valuable, but a correlated mistake is possible if one component of the source generator and its oracle share the same mistaken formula or type assumption. Phase 10 therefore introduces a separately written, minimal unsigned arithmetic oracle in `phase10/oracle.mjs`.

The independent oracle is deliberately plain `BigInt` arithmetic with modulo `2^width` and an explicit unsigned domain check. It does not use the FHEC AST, FHEC compiler, generated Solidity, TFHE runtime, CoFHE network, EVM bytecode or previous Phase 6 reference implementation. It covers:

| Family | Independent reference function | Important edge conditions |
| --- | --- | --- |
| `add` | `(a+b) mod 2^w` | identity, overflow, maximum |
| `sub` | `(a-b+2^w) mod 2^w` | equality, underflow, zero |
| `mul` | `(a*b) mod 2^w` | zero, identity, modular overflow |
| `gt` | `a > b` unsigned | less, greater, equal, boolean type |
| `max` | `a > b ? a : b` | both operand orders, equality |
| `repeated` | `(2*a*b) mod 2^w` | common subexpression and modular reduction |

The supported `w` values are precisely 8, 16, 32 and 64. Every operand and expected integer value is serialized as a decimal string, preserving u64 exactness in JavaScript and JSON. The `gt` output is a boolean in the canonical corpus and compared as an exact string only at the transport boundary with the SDK-returned boolean.

The repeated-expression formula is intentionally multiplication-based because the actual Phase 6 benchmark's `repeated` semantics are `2*a*b` modulo the width. That distinction matters for an *independent* oracle: a casual guess would validate the wrong operation. The Phase 10 implementation was cross-checked against the existing Phase 6 operation names and wrapper behavior, then independently exercised against compiled CoFHE mocks.

## C. Deterministic test data generation

For each of the 24 operation/width combinations, the first eight vectors come from a stable boundary schedule: zero/zero, maximum/one, one/maximum, maximum/maximum, `(maximum/2+1,maximum/2)`, zero/maximum, one/one and the reverse half boundary. For sample indices eight and above, the oracle derives two new masked BigInt operands from SHA-256 digests of the selected 64-character seed, width, operation and index, with separate domain tags for left and right.

This design is reproducible and does not depend on the machine's pseudo-random number generator, system locale, current time, or external network requests. It is not designed to be cryptographically secret or unpredictable; benchmark input values are intentionally public. The corpus contains the exact sample ID, width, operation, operation selector, input operands and expected result for every sample.

`-CasesPerFamily 2` produces 48 oracle cases. Two Solidity variants result in 96 mocked encrypted executions; three variants produce 144. `-CasesPerFamily 3` produces 72 cases, resulting in 144 or 216 mock executions. `-CasesPerFamily 8` produces 192 cases, resulting in 384 or 576 executions. The maximum supported setting is 16 cases per family, i.e. 384 cases and 768 or 1,152 mocked encrypted executions. These are **local tests**, not live paid testnet transactions.

The suite preserves six precomputed golden corpora: 2, 3 and 8 samples per family, with both optimized/tuned and optimized/tuned/straight variant configurations. The fixtures are regenerated and checked against the current independent oracle at every local verification. A mismatch prevents the Solidity mock suite from being treated as a valid reproducible run.

## D. Exact source and test flow

The accepted source is a Phase 8/9 preflight directory containing six known Solidity source files, the canonical Phase 8/9 plan, and its SHA-256 source seal. The new PowerShell verifier does not modify those files. It first verifies their full seal, then runs Node offline unit and adversarial tests, generates a new independent corpus into a unique `target/cofhe-phase1011-dossier-<run-id>` directory, and invokes an isolated Phase 8/9 Hardhat compilation with only the prepared source directory.

The Solidity contract implementations tested are exactly the existing wrapper symbols `FHECPhase6Live`, `FHECPhase7Tuned`, and optionally `FHECPhase7Straight`. The Phase 10 TypeScript test uses the pinned `@cofhe/sdk` from the existing lockfile to encrypt public test vectors for each particular consuming contract. The negative test intentionally binds an encrypted proof to the wrong consuming contract and expects the CoFHE mock execution to revert.

Each test case sends the equivalent operation selector and two encrypted inputs to every selected implementation, waits for its mock receipt, fetches the stored result handle, invokes SDK mock decryption and checks equality with the independent BigInt expected value. Only a successful, oracle-matched mock execution is appended to the observations. The suite records mock transaction gas, SDK mock encryption time and mock execution/decryption time, all clearly labeled as local measurements.

After the mocks finish, the source seal is reverified. The verifier copies the original prepared sources into the dossier as an immutable evidence snapshot and checks their copied source seal again. The saved raw result JSON is accepted only if it contains exactly the expected cases, in the right order, with the correct set of variant keys and positive decimal gas readings. The validation process independently reconstructs each expected result and both corpus/file hashes. Any missing sample, unknown variant, changed plaintext expectation or altered gas field aborts the run.

## E. Phase 10 modules

`oracle.mjs` is the independent reference arithmetic implementation and canonical test corpus generator. It accepts a bound on cases per operation/width family, exact comparison variant mode and explicit 64-character seed. Its parser validates the entire parsed corpus against a newly regenerated value. `verify-fixtures.mjs` checks the six reviewed snapshots without writing them. The two corresponding test files prove boundary correctness, determinism, seed sensitivity, strict unsigned range handling and rejection of mutated fixtures.

`FHECPhase10Properties.test.ts` is the Hardhat test harness. It imports the project's actual SDK and ethers Hardhat environment, deploys the already generated CoFHE wrapper contracts to local mocks, runs every canonical case, records measured local mock data and checks a wrong-consuming-contract proof. Its TypeScript compilation is scoped through `phase10/tsconfig.phase10.json`, which includes the relevant reviewed Phase 8/9 config and test to inherit required Hardhat/Chai augmentations without pulling unrelated older tests into the new gate.

`validate-results.mjs` is a separate local evidence validator, not invoked from inside the Solidity generator. It checks exact mock trace coverage and source/corpus fingerprints, recomputes operation expectations and every mock gas summary, then writes a JSON result only after a complete successful test run. It uses BigInt to sum potentially large gas figures and makes no conversion to a testnet receipt or a fiat price.

## F. Phase 11 modules

`report-html.mjs` creates a self-contained offline HTML comparison from the validated local mock output. It groups the 24 operation/width families into a readable table, reports sample counts and median **mock** gas by implementation, and escapes all dynamic fields to prevent injected HTML or scripts in the report.

`readiness.mjs` emits explicit evidence gates without inventing a software-completion percentage. It marks source provenance, independent arithmetic oracle coverage, local mock differential correctness and self-contained local evidence as locally verified, while requiring external evidence for actual live testnet receipts, coprocessor fees, hosted CI and independent security review. Grant approval remains outside the tool's control.

`attest.mjs` takes a complete dossier directory, regenerates the Phase 8/9 source seal, reconstructs the Phase 10 canonical corpus, revalidates the raw mock observations, recomputes the rendered HTML and readiness gates, and hashes all 13 fixed evidence files. It creates an offline manifest with exact bytes and SHA-256 for each file and its canonical aggregate inventory. Its `--verify` mode reruns the entire sequence from scratch without a private key, RPC account, Hardhat test process or network call.

The verifier accepts neither a list of arbitrary filesystem paths nor user-supplied commands. The evidence inventory is fixed by the reviewed script, and regular-file checks reject symlinks and non-file entries. The bundle uses a fresh unique directory, avoiding collisions and historical overwrites.

`audit-phase11.ps1` offers a straightforward Windows entry point for read-only re-auditing. It verifies a known evidence directory but does not install source, reset Git history, send a transaction or mutate the dossier.

## G. Evidence layout and integrity

The complete dossier contains `corpus.json`, `mock-observations.json`, `validated-mock-results.json`, `offline-report.html`, `readiness-gates.json`, `phase11-evidence-manifest.json` and a `sources` directory with all six Solidity files, the Phase 8/9 plan and the source seal. The manifest covers the other 13 files; its own bytes are excluded to avoid circular hashing. The aggregate fingerprint is a hash of a canonical ordered inventory of filenames, byte counts and SHA-256 hashes.

This is a reproducibility mechanism, not a trusted timestamp, third-party digital signature or proof that a developer is honest. A malicious party who can alter both the full dossier and the verifier source can fabricate a locally consistent report. For greater assurance, publish an immutable version control commit and independently hash/attest the source in hosted CI and from a second machine, then compare results.

The two previous sources of local truth remain distinct: the Phase 8/9 prepared source report proves which source files were generated and mock-preflighted; the Phase 10/11 corpus and observations prove the new independent property sample outcomes under the installed CoFHE mocks. Successful offline dossier verification does **not** promote those mock results into actual Fhenix coprocessor or Arbitrum Sepolia execution evidence.

## H. Acceptance gates

**10.1:** The exact reviewed Phase 8/9 baseline hashes match; no old source is modified. **10.2:** A successful Phase 8/9 `prepared-phase89.json` with matching source seal is present. **10.3:** The six golden sample fixtures regenerate from the independent reference oracle. **10.4:** All new Node unit/adversarial tests pass. **10.5:** The new TypeScript test harness passes its scoped typecheck against pinned SDK packages. **10.6:** The actual source-sealed compiled CoFHE wrapper mock tests pass for the selected corpus and all variants. **10.7:** A ciphertext encrypted for the wrong consuming contract is rejected. **10.8:** Missing or corrupted results fail independent validation.

**11.1:** The exact source snapshot remains sealed after mock execution. **11.2:** The complete 24-family output is present and correctly identified. **11.3:** The HTML report contains exact mock-only limitations and no HTML injection. **11.4:** The readiness gates do not promote mock results to a live claim. **11.5:** The 13-file evidence manifest regenerates and verifies independently. **11.6:** A one-byte alteration to a source file, corpus, observation, validation or HTML output is detected. **11.7:** The standalone offline audit requires no wallet or network and does not mutate existing evidence.

## I. Residual risks

Randomized and boundary testing cannot prove correctness for every unsigned input combination, especially 64-bit domains. These tests do not check signed types, additional encrypted widths not supported by the existing backend, arbitrary loops, distributed operations, concurrency, protocol oracle availability, key recovery or side-channel resistance. The independent arithmetic oracle and CoFHE mock code could both be correct while a live protocol integration fails due to RPC, proof verification, signer permissions or asynchronous decryption availability.

The toolchain remains pinned to the user's installed dependency lockfile; SDK upgrades require a separate compatibility sprint. Mock gas is not live gas, and native EVM transaction gas is not necessarily the main economic unit for off-chain FHE coprocessor work. Hosted Windows/Linux CI and independent external security review remain unverified until separately completed.

The appropriate completion statement is that **Phase 10/11 adds reproducible, source-sealed, independently validated local CoFHE property testing across sampled operations and supported widths**. It does not make the entire FHEC V2 compiler, all backends, the CoFHE ecosystem, or a $20,000 grant unequivocally complete.
